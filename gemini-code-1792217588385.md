## 2. Product Requirements & Key Architectural Decisions

### Problem Summary

Operations teams at Nimbus Freight are overwhelmed by alert noise from refrigerated truck sensors. We need a stateful alert management engine that suppresses transient spikes (blips) and eliminates alert fatigue by deduplicating and consolidating sustained temperature violations.

### Technical & Domain Assumptions

1. **Temperature Threshold**: Standard cold-chain pharmaceutical/grocery range is 2.0°C – 8.0°C. Any reading > 8.0°C is an active excursion.
2. **Sustained Duration Window**: A alert triggers ONLY if readings remain > 8.0°C for a continuous duration of $\ge 15\text{ minutes}$ (or 3+ consecutive out-of-bounds readings).
3. **State Machine / Alert Lifecycle**:
   - `OK`: Truck operating within normal temperature limits.
   - `PENDING_VIOLATION`: High reading detected, but sustained duration threshold (15 min) not yet met.
   - `ACTIVE_ALERT`: Sustained excursion confirmed. Alert raised once.
   - `RESOLVED`: Temperature drops back to $\le 8.0^\circ\text{C}$ for 2 consecutive cycles.
4. **Out-of-Order & Gap Handling**:
   - Telemetry data processed by sorting inbound batches by `timestamp` per `truck_id`.
   - Gaps $> 30\text{ minutes}$ without telemetry trigger a separate `CONNECTION_LOST` alert.

## 4. End-to-End Implementation Deliverables

### Phase 1: Backend Data Models & Core Engine Logic (`/backend`)

1. **DB Schemas (`models.py`)**:
   - `Truck`: `id`, `vin`, `driver_name`, `cargo_type`.
   - `TelemetryReading`: `id`, `truck_id`, `temperature_c`, `latitude`, `longitude`, `timestamp`.
   - `Alert`: `id`, `truck_id`, `state` (`ACTIVE`, `RESOLVED`), `started_at`, `resolved_at`, `peak_temperature`, `summary`.
2. **Alert Engine Logic (`engine.py`)**:
   - Stateful processing function `process_readings(truck_id, readings_list)`.
   - Deduplication logic preventing re-triggering while an alert is active.
   - Natural language summary generation for alerts (e.g., _"Truck T-04 cargo exceeded 8.0°C for 22 mins with peak at 11.4°C"_).

### Phase 2: FastAPI REST API Endpoints (`/backend/main.py`)

- `POST /api/v1/telemetry/ingest`: Ingest seed dataset or batch readings.
- `GET /api/v1/alerts`: Query active and historical alerts with filters (`truck_id`, `status`).
- `GET /api/v1/trucks/{id}/timeline`: Fetch temperature history vs alert overlays for charts.
- `POST /api/v1/engine/run`: Triggers full engine evaluation over the dataset.

### Phase 3: Frontend Dashboard UI (`/frontend`)

- Styled using SCSS modules + React-Bootstrap according to the Velvet template archetype.
- **Components**:
  - `MetricCards`: High-level metrics (Total Active Alerts, Fleet Status, Average Temp).
  - `AlertsTable`: Filterable, badges for severity/status, expandable details showing the LLM-style human readable summary.
  - `TemperatureChart`: Recharts line plot showing normal threshold lines (2°C - 8°C) vs actual truck temp timeline with active alert shading.
  - `SidebarNav`: Fleet Overview, Alert Center, System Logs.

### Phase 4: Documentation

- `SOLUTION_DESIGN.md`: Document problem statement, domain choices, edge case trade-offs, and future improvements.
- `README.md`: Setup commands, dataset ingestion guide, execution steps.
